# UI

**Mobile-first. Not mobile-responsive — mobile-first.** The phone layout is the
real design; desktop is the same layout with a max-width and more breathing
room. There is no desktop-specific view and none is planned.

**Hard ceiling: 5 screens.** Adding a sixth means removing one or merging two.
This is a real constraint, not aspirational — screen-hopping to complete a
single action is the specific failure mode this design exists to avoid.

---

## Screen Inventory

| # | Screen | Route | Purpose | How often |
|---|---|---|---|---|
| 1 | **Login** | `/login` | Username + password | Once every 90 days |
| 2 | **Chat** | `/` | The conversation. Everything happens here | Constantly |
| 3 | **Desktop** | `/desktop` | Live view of the sandbox desktop | While E2E runs |
| 4 | **Project** | `/project` | Repo, sandbox, usage, danger zone | Rarely |
| 5 | **Settings** | `/settings` | Config, model, prompt, credentials | Rarely |

Navigation is a **fixed bottom tab bar with 4 tabs** (Chat, Desktop, Project,
Settings). Fixed, not contextual — tabs that appear and disappear force you to
re-learn the layout every time, which is exactly the wrong trade for this
operator. Login sits outside the tab bar; it is not a place you navigate to.

### What is *not* a screen

Deliberately folded into Chat rather than given their own screens:

- **Goal plan approval** — renders inline as a card in the conversation with
  Approve / Reject. Approving a plan should never mean leaving the conversation.
- **Diffs** — inline, collapsed by default, tap to expand.
- **Tool calls** — inline in the timeline, collapsed, tap for detail.
- **Ask-human** — an ordinary message. No modal, no separate inbox.
- **Preview URL** — a pinned chip in the Chat header once available.
- **Cost / tokens** — compact strip in the Chat header; the full breakdown lives
  on Project.
- **Onboarding / setup wizard** — there isn't one. Settings *is* setup, and it
  works while half-filled.

## 1. Login

Username, password, submit. Nothing else — no signup, no forgot-password, no
branding.

Failed attempts are rate-limited. On success, sets a 90-day session cookie so
the installed PWA effectively stays logged in.

While the password is still the default `doot`/`doot`, a dismissible banner
appears on Chat. It nags; it does not force a change.

## 2. Chat — the home screen

The default route. 90% of all time is spent here. It must work with one thumb.

**Header (compact, sticky):**
- Project name
- Run status pill: `idle` / `running` / `paused` / `awaiting you` / `error`
- Preview URL chip, when a preview is live
- Session cost + context-usage percentage

**Body — one continuous timeline**, newest at the bottom:
- My messages and agent messages
- Tool calls as compact rows: name, status, duration. Collapsed by default.
- Diffs, collapsed, with file + line counts on the summary row
- Plan cards with inline Approve / Reject
- Reviewer verdicts as compact inline notes
- Screenshots from computer-use, inline thumbnails
- Compaction and clear events as thin dividers, so context boundaries are
  visible rather than mysterious

**Footer:**
- Text input + send
- **Pause** — replaces send while a run is active. One tap, always reachable,
  never behind a menu.
- Overflow menu (the only menu in the app): Clear Conversation, Create Goal Plan

Collapsed-by-default is the core rule here. The timeline must stay scannable on
a 6-inch screen; expanding is opt-in.

## 3. Desktop

Live noVNC view of the sandbox desktop, embedded full-screen with the tab bar
overlaid.

This exists as its own screen because watching the E2E verifier actually drive
the UI is the highest-signal debugging tool available, and it cannot be usefully
embedded in a chat bubble on a phone.

- Shows a clear placeholder when the sandbox is stopped or computer-use isn't
  running, with a single button to start it.
- Read-only by default; an explicit "take control" toggle enables input, so I
  can't fight the agent for the mouse by accident.
- Screen recordings from past E2E runs are listed here for playback — they're
  stored in R2, so they outlive the sandbox.

## 4. Project

Doubles as **Create Project** when no project exists — same route, different
state. There is no separate creation screen because creation happens once.

**Empty state:** name + repo URL → Create. That's the whole form. It provisions
the persistent sandbox.

**Populated state:**
- Repo, base branch, work branch (`doot`), last pushed SHA, PR link if any
- Sandbox: ID, state, size, resolution, last activity. Start / Stop buttons.
- Setup script and dev command / port, editable
- Usage: cost and tokens broken down by purpose (primary / reviewer / E2E /
  compaction), plus recent runs
- **Danger zone**, visually separated, each action individually confirmed:
  Reset Sandbox, Delete Project

Reset Sandbox and Clear Conversation live on different screens *on purpose*.
They are unrelated operations, and putting them side by side would make
mistaking one for the other easy.

## 5. Settings

One scrolling form, grouped, saving per-section:

- **Account** — username, change password
- **Model** — model name, base URL, API key, context window, max output tokens
- **Agent** — system prompt, compaction threshold, reviewer on/off, E2E on/off
- **Sandbox defaults** — snapshot, auto-stop minutes, VNC resolution
- **Git / GitHub** — PAT, username, commit author, create-PR toggle
- **Pricing** — input / cached-input / output cost per Mtok

Secrets render as masked fields showing only whether a value is set. Saving a
blank secret field leaves the existing value alone; clearing requires an
explicit Remove. This matters because the primary use case is pasting a rotated
PAT from a phone, and an accidental blank submit wiping credentials would be
infuriating.

## Live Updates — SSE

**SSE, not WebSockets.** Updates flow one direction only; user actions are
ordinary form POSTs. A single user means no fanout concerns. WebSockets would
add a protocol, a heartbeat scheme, and reconnect logic for no benefit.

**Endpoint:** `GET /events` — one stream per connected client.

**Event types:**

| Event | Payload |
|---|---|
| `run.status` | run id, status, plan/task progress |
| `message.append` | new message (rendered HTML fragment) |
| `message.delta` | streaming token delta for the in-flight assistant message |
| `tool.start` / `tool.end` | tool name, status, duration |
| `diff` | file path, collapsed diff fragment |
| `plan.proposed` / `plan.updated` | plan card fragment |
| `task.updated` | task id, status, review verdict |
| `screenshot` | artifact URL, dimensions |
| `sandbox.state` | sandbox state transitions |
| `usage` | running cost + context percentage |
| `epoch.changed` | clear/compact boundary marker |

Payloads are **pre-rendered HTML fragments**, not JSON, so htmx swaps them
directly and there is no client-side rendering layer to keep in sync with the
server templates.

### Reconnect — the part that actually matters on mobile

Every event's SSE `id` is the `events.id` primary key from the database.

Mobile browsers kill background connections aggressively — locking the phone
ends the stream. So:

1. Client reconnects automatically and sends `Last-Event-ID`.
2. Server replays `SELECT * FROM events WHERE id > ? ORDER BY id`, then
   continues live.
3. Nothing is lost, and no full page reload is needed.

Without the durable `events` table this would be impossible, which is why it's
part of the schema rather than an in-memory ring buffer. An in-memory buffer
would also be wiped by any Fly machine restart.

If the gap is too large to replay sensibly (or the events have been pruned), the
server responds with a `reload` directive and the client re-fetches the
timeline.

**Practical requirements:**
- `Cache-Control: no-cache`, `X-Accel-Buffering: no`, and explicit flushing per
  event — mobile carrier proxies and Fly's edge will otherwise buffer and the
  stream will appear frozen.
- Keepalive comment (`:ping`) every 15 seconds to stop idle-connection reaping.
- On `visibilitychange` → visible, force a reconnect rather than trusting that
  the existing connection survived.

## PWA

Installable to the home screen. This is a primary requirement — the app should
launch like an app, not a bookmark.

**Manifest:** `display: standalone`, `start_url: /`, portrait orientation,
theme + background colors, 192px and 512px icons plus a maskable variant.

**Service worker — narrow scope on purpose:**
- Precache the app shell only: CSS, JS, fonts, icons.
- **Never cache `/api/*`, `/events`, or any HTML.** A cached conversation or a
  cached run status is worse than no data — it would show stale agent state and
  I'd act on it.
- Network-first for navigation, with an offline fallback page.
- Offline state is shown honestly: a banner saying the connection is down, not a
  UI that pretends to work.

**Explicitly out of scope:** push notifications, background sync, offline
queuing of messages. The ask-human tool parks the run and waits visibly; that is
the entire notification design.

## Style

- Dark by default. No theme switcher.
- System font stack. No web fonts in the critical path.
- One accent color. Status is communicated by a small set of consistent pills.
- Generous tap targets (44px minimum).
- No animation beyond a streaming-cursor and collapse/expand.
- No skeletons, no spinners-within-spinners, no toasts stacking up.

The bar for adding any visual element: does it tell me something I need to act
on right now? If not, it doesn't ship.
